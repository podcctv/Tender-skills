# Tender-skills

面向投标/售前方案编制的可移植 AI skill。核心 skill 名称为 `tender-bid-writer`，用于让 Codex、OpenClaw、Hermes 等 agent 从招标文件中抽取需求、生成投标方案框架、编写章节、合稿质检、模拟专家评审并输出交付清单；配套的 `cn-government-procurement-bid-format` 专门处理政府采购投标文件格式、固定表格、签章与提交检查。

流程将“需求抽取 -> 章节 brief -> 人工确认 -> 逐章编写 -> 合稿 -> 质检 -> 多专家评审 -> 多轮修订 -> 最终交付”固化为一个可复用的 skill。

## 适用场景

使用这个 skill 处理以下任务：

- 分析招标文件、评分办法、技术规范、商务条款、资格要求。
- 解析投标文件组成、官方响应表格、默认排版、页码目录、签字盖章、电子/纸质提交和最终 Word/PDF 格式风险。
- 接到外包/代写标书时，先审招标文件，输出对客户的标书框架、资料清单、评分点响应关系和风险反馈。
- 在编写前判断项目属于 `goods-mode`、`software-platform-mode`、`hybrid-goods-software-mode` 或 `service-mode`。
- 将采购需求拆解到三级：一级需求域/系统边界，二级功能或服务事项，三级最小响应单元。
- 生成投标技术方案、服务方案、实施方案、运维方案、培训方案等框架。
- 建立评分点/响应点/证据材料的追踪矩阵。
- 按厚标书标准逐章编写 HTML、Markdown 或 DOCX 目标稿件。
- 合稿后进行占位符、漏项、证据缺口和一致性检查。
- 模拟合规、技术、评分、交付、商务/法务等多专家评审。
- 对长标书使用稳定任务 ID、输入哈希、日志、局部结果和断点恢复，避免中断后从头开始或覆盖成功结果。
- 对全局事实、知识库复用和跨章节一致性实行证据门禁；只允许 `evidence-backed`、`placeholder`、`omit`，不允许 `fabricate`。
- 对电子投标文件执行“范围划分—证据核对—结论收敛”三轮否决风险检查，并将纸质装订、密封、现场动作单独列出。
- 在招标文件静默时提供标准、正式装订、宽表格等条件型版式兜底；紧凑评审和图文方案只作用户明确选择后的参考，明确要求始终优先。

## 核心写作标准

- 招标文件是唯一事实源。不得编造资质、证书、案例、人员、价格、工期、授权、签章状态或第三方承诺。
- 外包/代写项目必须先做前置审标。没有拿到客户材料前，只能形成审标报告、框架、资料清单、评分映射和反馈问题，不能把缺失证据写成正式承诺。
- 先判断投标模式，再决定抽取方式、证据矩阵、目录结构、篇幅规划、正文密度和质检规则。
- 采购需求必须先细化到三级。第三级应能直接对应正文小节、响应证据、交付物或验收点。
- 无招标页数硬限制时，按项目价值、项目复杂度和投标模式规划整标篇幅。软件平台标和复杂混合标可用 `1 万元 ≈ 1 页` 作为基础测算；重大软件平台/复杂混合项目原则上不低于约 `300-500 页`。货物标不机械套用长正文，页数主要来自参数表、证据矩阵和附件材料完整度。
- 最小正式正文小节通常不少于 `3-5 段`。货物标参数响应、固定格式表、符合性声明或招标要求短答除外。每段应有机制、场景、执行细节、表单记录、风险控制或验收支撑，不能只换说法重复标题。
- 表格必须服务评审和落地，例如需求响应矩阵、接口联调检查表、数据质量检查表、风险预防表、交付文档清单、验收映射表。
- 正式章节不得出现 `TODO`、`待确认`、`公司名称`、`项目名称：填写`、`如有证据再补` 等内部草稿痕迹。
- 格式规则必须分层记录为招标文件/平台强制、原生模板、默认建议或待核实；招标文件没有明确要求时才使用默认格式，不能把“小四宋体”、A4、胶装、逐页盖章等行业习惯冒充强制要求。

### 格式专项 skill 的调用

只做投标文件格式、响应表、签章或提交检查时，可直接调用 `$cn-government-procurement-bid-format`。使用 `$tender-bid-writer` 进行完整审标或编标时，遇到上述内容应同步采用该专项 skill 的规则。两者均遵循同一优先级：适用法律和平台强制规则、最新招标文件及澄清更正、招标文件原生模板，最后才是默认建议。

## 外包标书前置审标流程

当标书是别人外包给你写，或对方只给了招标文件、还没有提供公司资质/业绩/人员/产品/授权/方案素材时，不要直接写正式正文。先用 skill 做一轮“审标 + 要材料 + 内部组织”。第一轮默认只输出两份文件，避免给客户散发一堆难以执行的表格。

### 第一轮必须输出

| 输出物 | 用途 |
| --- | --- |
| `资料清单（项目名称）.docx` | 发给客户的唯一主文档。把项目摘要、紧急 P0 提醒、必须提供/确认项、评分项资料、行业专项资料、客户填写表、招标原生表格、签章提交要求、可暂缓材料、回传规则和问题清单都收进去 |
| `标书组织说明（项目名称）.md` | 写标方内部使用。放完整审标逻辑、投标模式、提交方式、废标项、评分映射、目录框架、页数预算、证据依赖、可写承诺边界、问题和下一步计划 |

客户只需要收到 Word 资料清单；Markdown 是自己组织标书用的，不作为对外沟通文档。原来那些招标文件审查报告、废标项清单、评分点响应映射表、提交方式与签章盖章要求表、问题澄清清单等内容，第一轮应分别收进这两个文件里，而不是拆成很多附件。

资料优先级：

- `P0`：资格、否决项、强制格式、授权、签章、承诺函等硬性材料；必须提供，否则废标或高概率无效投标，缺失时不能假定满足。
- `P1`：直接影响评分的关键材料，如业绩、人员证书、产品证明、检测报告、案例、方案素材。
- `P2`：支撑可信度和润色的辅助材料，如公司介绍、获奖、宣传册、一般制度文件。

资料必要性分类：

| 分类 | 含义 | 反馈口径 |
| --- | --- | --- |
| `must-provide-or-reject` | 招标文件要求必须提交的资格、否决项、授权、签章、格式、强制附件等 | 明确告诉客户“必须提供，否则废标/高概率无效投标” |
| `must-respond-can-commit` | 必须在标书中响应，但招标文件未强制要求单独附件 | 可通过正式响应、承诺函、方案说明支撑，但必须确认承诺边界 |
| `scoring-critical` | 不一定废标，但直接影响评分 | 明确缺失会丢分或削弱得分 |
| `optional-supporting` | 辅助证明、润色材料 | 可不提供，但说明可能影响可信度或文本饱满度 |
| `not-needed-now` | 当前阶段不需要或招标文件未要求 | 不主动向客户索要，避免增加沟通负担 |

### Word 资料清单生成规则

如果招标文件提供了响应文件组成、固定格式、报价表、资格声明、授权委托、业绩表、人员表、车辆/设备表、产品参数响应表、服务承诺表、偏离表等表格，资料清单必须按当前招标文件的格式来生成，不能只输出通用“请提供某某证件”。

如果招标文件或投标文件格式模板本身是 Word/DOCX，客户填写包里的表格也应优先做成 Word 原生表格，尽量保留原表的标题、顺序、合并单元格、列名、行名、空白填写格、包号、单位、备注、签字盖章位置和填表说明。不要把招标文件里的正式 Word 表格压扁成普通清单；需要给客户的提示可以放在表格前后或单独的“填报说明/写作控制表”里。

生成资料清单时应分两层：

- **客户填写层**：保留招标文件里的表格名称、字段、列名、单位、包号、签字盖章位置、备注说明和填报口径，让客户可以直接按表填写或提供附件。
- **写作控制层**：在单独的说明或跟踪表里标注来源条款、资料必要性、P0/P1/P2 优先级、缺失后果、目标章节、是否已收到、质量检查意见。

默认交付格式：

- 主文件默认生成 Word：`资料清单（项目名称）.docx`。Word 适合客户填写、转发、打印、签字盖章和回传。
- 当源文件为 Word/DOCX 时，主文件里的客户填报表应采用 Word 表格形态，能让客户按招标文件原表逐项填写或补附件；历史资料清单样例只能参考排版和话术，不能替代当前招标文件的表格抽取。
- 第一轮不默认另附 Excel。若存在大量结构化明细，先在 Word 中说明是否建议拆出 Excel，只有用户明确要求时再另做 `资料填报明细表（项目名称）.xlsx`。
- 内部组织文件默认生成 Markdown：`标书组织说明（项目名称）.md`，用于保存审标、评分映射、目录框架、页数预算和证据状态。

必须遵守：

- 每份标书的资料清单都应从当前招标文件重新抽取，不得机械套用历史项目模板。
- 用户提供的历史资料清单模板只能参考版式和表达方式，不能复制其中的项目专属资料项。
- 对表格类材料，应按招标文件原表颗粒度索取数据。例如开标一览表、分项报价表、业绩表、人员配置表、车辆设备表、仓储能力表、技术参数响应表等，都应单独生成客户填写项。
- 如果招标文件表格字段不清晰、附件缺失或扫描不可读，应列入问题澄清清单，不得自行编造字段。

### 食材配送资料清单模板

当前第一版优先完善食材配送、食堂食材、主副食品、粮油生鲜、食材集中采购类项目。`资料清单（项目名称）.docx` 建议按下面结构组织：

1. 封面与紧急提醒：项目名称、截止时间、资料回传时间、P0 必办事项、报价/下浮率确认、签章上传提醒。
2. 使用说明：客户如何填写、扫描、命名、回传；P0/P1/P2/可暂缓的含义。
3. 必须提供或必须确认的资料：营业执照、食品经营/生产许可或备案、法人/授权、社保、税费、财务、信用、保证金、平台账号、有效期、无偏离、公平竞争、不挂靠不转包等。
4. 评分项对应资料清单：业绩、车辆、人员、仓库、食品安全、保险、检测设备、体系认证、荣誉、服务方案素材等逐项对应分值。
5. 食材配送专项资料：供应渠道/合作供应商、肉类检疫、生鲜农残检测、粮油质检、冷链溯源、非转基因证明或承诺、包装标签照片、剩余保质期、临时加送、未列明食材和易耗品供货能力。
6. 客户需填写的基础信息与确认表：单位信息、联系人、开户税号、开票能力、平台操作人、B2B 支付能力、报价承受能力、售后联系人。
7. 招标文件原生表格及填报项：开标一览表、分项报价表、承诺函、偏离表、业绩表、人员/车辆/仓库表等，按当前招标文件 Word 表格复刻。
8. 可暂缓或有则提供的补充材料：发票、验收单、配送记录、客户评价、宣传册、制度文件等，并说明不提供的影响。
9. 回传清单与下一步：文件命名规则、回传截止、二次补件流程、仍需确认问题。

### 电子标/纸质标的签章规则

前置审标时必须先判断投标提交方式，并输出“提交方式与签章盖章要求表”：

- `electronic-bid` 电子标：重点确认平台账号、CA/数字证书、电子公章、法定代表人或授权代表电子签名权限、上传操作人、在线签到/开标联系人、文件格式、大小限制、加密、解密、保证金/平台费用、上传截止时间和应急联系人。电子标通常在上传或平台制作阶段进行电子签章，不默认要求客户把所有文件手写签字盖章后扫描，除非招标文件明确要求随电子标上传签字盖章扫描件。
- `paper-bid` 纸质标：重点确认法定代表人或授权代表签字、公司盖章、逐页盖章或骑缝章、正副本数量、装订方式、封面/密封袋标签、密封章、递交地址、递交人、递交截止时间，以及哪些资料必须先由客户签字盖章后回传给写标方。
- `dual-bid` 电子+纸质双轨：同时执行电子标和纸质标检查，并增加一致性校验，确保投标人名称、项目/包号、报价、日期、授权人、承诺内容、附件编号、最终版本时间或文件哈希在电子版和纸质版之间一致。

客户资料包中每个表单或附件都应标注其签章状态：`纸质签字盖章`、`电子签章`、`需签章扫描件`、`仅填信息`、`平台提交时签章`。这些标注必须对应招标条款和缺失后果，不能凭习惯要求客户多做无关盖章。

### 外包资料补充确认项

真实项目中，资料清单除了资格证照、业绩合同、信用报告、保证金凭证、报价和售后联系人等大项，还应补充以下操作类和关联关系类确认：

| 补充项 | 建议级别 | 用途 |
| --- | --- | --- |
| 响应单位基础信息表：单位全称、注册地址、通讯地址、联系人、电话、邮箱、员工人数、开户行、账号、税号、开票类型 | P0 | 响应人概况、报价表、授权书、合同信息、开票信息都会复用，建议做成客户填写表 |
| 关联关系与公平竞争确认 | P0 | 确认与采购人不存在影响公正性的利害关系；确认不与其他响应单位存在同一负责人、控股或管理关系 |
| 不挂靠、不转包、不分包确认 | P0 | 若招标文件禁止挂靠、转包、分包，应要求客户书面确认，避免中标后取消资格或合同风险 |
| 平台操作人确认 | P0 | 明确注册、报名、下载文件、上传响应文件、在线签到、开标当天应急联系人和联系电话 |
| 保证金/平台费用支付能力确认 | P0 | 确认付款账户、支付路径、截止时间，以及网银/B2B 支付能力是否已开通 |
| 响应有效期确认 | P0 | 若招标文件规定有效期，要求客户确认接受该有效期 |
| 无偏离/无附加条件确认 | P0 | 确认接受合同条款和采购要求，不提出差异表未明示的偏差或附加条件 |
| 信用及诉讼类辅助截图 | P1 | 若招标文件列出多个信用/诉讼查询渠道，强制报告按 P0，辅助截图通常按 P1 增强稳妥性 |
| 人员健康证、安全证、操作证等行业证件 | P0/P1 | 招标要求投标时上传则为 P0；未强制上传但履约需要则为 P1，并要求客户承诺投入人员持有效证件 |
| 类似业绩辅助证明：中标通知书、发票、验收单、配送/服务记录、客户评价 | P1 | 证明合同真实性和履约能力，避免只有合同扫描件显得单薄 |
| 报价成本承受能力/内部测算表 | 内部 P0 | 下浮率或价格分占比高时必须内部测算人工、运输、损耗、税费、利润和履约风险；除非招标要求，不随标提交 |

### 食品/食材配送类补充证据

遇到食堂、食品、粮油、生鲜、食材配送、易耗品供应等项目时，除通用资料外，应额外检查：

- 供应渠道/合作供应商清单、来源追溯方式。
- 食品经营许可证、生产许可证或相关资质是否覆盖采购范围。
- 配送人员健康证；如投标阶段不能全部提供，至少要求书面确认投入人员具备有效健康证并按要求补齐。
- 肉类检疫合格证明、生鲜果蔬农残检测样例、冻品冷链溯源材料、粮油干货质检报告。
- 食用油非转基因承诺或包装/检测证明样例，尤其招标文件明确要求非转基因时。
- 粮油及包装食品标签照片样例，包括 SC/QS 标识、生产厂家、生产日期、保质期、剩余保质期要求。
- 未列明食材、食堂易耗品、临时加送和应急补货能力说明。
- 过往配送清单、验收单、发票、客户评价或长期供货证明，有则作为 P1 辅助履约证明。

推荐提示词：

```text
使用 $tender-bid-writer 按外包标书前置审标流程处理这个项目。现在先不要写正式标书正文。请先审招标文件，判断投标模式和提交方式，第一轮只输出两份文件：一份给客户的 Word《资料清单（项目名称）.docx》，一份自己组织标书用的 Markdown《标书组织说明（项目名称）.md》。Word 资料清单要参考食材配送资料清单的客户沟通结构，包含项目摘要、紧急 P0 提醒、必须提供或必须确认资料、评分项对应资料、行业专项资料、客户填写表、招标文件原生表格、电子标/纸质标的签章提交要求、可暂缓材料、回传清单和问题清单；如果招标文件是 Word/DOCX，请尽量复刻其原 Word 表格的标题、列名、合并单元格、填写格、备注和签字盖章位置。Markdown 文件放完整审标逻辑、废标项、评分映射、目录框架、页数预算、证据依赖、可写承诺边界和下一步计划。不要默认拆出 Excel，除非我另行要求。
```

### 客户回传材料后的第二轮

拿到客户材料后，先核对材料，不要马上合稿。

推荐提示词：

```text
使用 $tender-bid-writer 根据客户新提供的材料更新前置审标结果。请逐项核对资料清单，标注已收到、可用、不完整、过期、与要求不一致或仍缺失；同步更新评分点响应映射表、章节 brief 和可正式写入正文的承诺范围。对仍缺失的材料输出二次追问清单。
```

第二轮确认后，再进入逐章正文编写。

## 四种投标模式

使用这个 skill 时，第一步先让 agent 判定模式。模式会控制后续需求抽取、证据准备、目录框架、篇幅规划和质检重点。

| 模式 | 适用场景 | 核心材料 | 写作厚度 |
| --- | --- | --- | --- |
| `goods-mode` 货物标 | 采购设备、硬件、成品软件、标准产品、耗材、仪器等 | 产品彩页、检测报告、厂家授权、参数响应表、证书、质保、供货安装方案 | 最固定，重点是参数、证据、偏离表，正文不宜虚胖 |
| `software-platform-mode` 软件平台标 | 定制开发、系统集成、数据中台、业务平台、AI 能力中心、软件运维平台等 | 需求分析、总体架构、功能设计、业务流程、数据/接口/安全/实施/验收方案 | 最适合厚标书，按功能、流程、数据对象和场景大篇幅展开 |
| `hybrid-goods-software-mode` 货物+软件混合标 | 既有硬件设备/成品产品，又有平台开发、集成、部署、服务 | 产品参数材料 + 平台方案 + 集成部署 + 联调验收 | 拆成产品响应线、软件方案线、集成交付线，不能混写 |
| `service-mode` 服务标 | 运维、咨询、规划、培训、测评、监理、数据治理、驻场服务等 | 服务范围、人员、SLA/KPI、流程、工具、记录、报告、考核、验收 | 中到厚，重点是人员、流程、记录、考核、风险和验收 |

模式判断推荐提示词：

```text
使用 $tender-bid-writer 先判断本项目属于 goods-mode、software-platform-mode、hybrid-goods-software-mode 还是 service-mode。请说明判断依据，并按对应模式列出需求抽取表、证据清单、目录框架和页数规划。先不要写正文。
```

### goods-mode 货物标

货物标的核心不是长篇架构，而是参数、型号、品牌、证据和偏离控制。

推荐产物：

- 参数响应表
- 产品证据矩阵
- 品牌/型号/规格清单
- 检测报告、彩页、官网截图、证书、授权材料清单
- 偏离表和负偏离风险表
- 供货、安装、调试、培训、验收安排
- 售后服务与质保承诺

推荐提示词：

```text
使用 $tender-bid-writer 按 goods-mode 处理本项目。请优先抽取技术参数、品牌型号、规格要求、证据材料、授权质保、供货安装、调试培训和验收要求，生成参数响应表、产品证据矩阵、偏离风险表和交付清单。不要写成软件平台架构方案。
```

### software-platform-mode 软件平台标

软件平台标适合厚写，要体现业务理解、总体架构、功能模块、数据对象、接口关系、安全、实施、演示、验收和运维。

推荐提示词：

```text
使用 $tender-bid-writer 按 software-platform-mode 处理本项目。请将采购需求拆到三级，按业务场景、功能模块、数据对象、接口关系、安全控制、实施迁移、演示支撑、验收映射和运维服务生成厚标书目录、页数预算和章节 brief。
```

### hybrid-goods-software-mode 混合标

混合标必须拆三条线，避免把硬件参数藏进软件章节，也避免把软件集成写成简单供货。

三条线：

- 货物/产品响应线：型号、品牌、参数、彩页、检测报告、授权、质保、供货。
- 软件/平台方案线：架构、功能、数据、接口、安全、实施、演示、验收。
- 集成交付线：设备安装、软件部署、接口联调、系统测试、培训、试运行、最终验收。

推荐提示词：

```text
使用 $tender-bid-writer 按 hybrid-goods-software-mode 处理本项目。请拆成货物/产品响应线、软件/平台方案线和集成交付线，分别输出需求台账、证据矩阵、目录框架、责任矩阵、联调验收计划和页数预算。
```

### service-mode 服务标

服务标不要硬套产品参数表，也不要强行写成平台开发。重点是服务范围、人员组织、SLA、流程记录、考核验收和风险处置。

推荐提示词：

```text
使用 $tender-bid-writer 按 service-mode 处理本项目。请抽取服务范围、人员资质、驻场/远程安排、SLA/KPI、服务流程、响应升级、过程记录、报告节奏、考核办法、培训交接和验收要求，生成服务方案框架和证据清单。
```

## 模式设计依据

四模式规则参考了政府采购制度中的几个基础口径：

- [《政府采购需求管理办法》](https://m.mof.gov.cn/czxw/202105/t20210510_3699403.htm)：采购需求包括采购标的及其技术、商务要求，技术要求覆盖功能和质量，商务要求覆盖交付、付款、包装运输、售后服务等。
- [《政府采购货物和服务招标投标管理办法》财政部令第 87 号](https://www.mof.gov.cn/gp/xxgkml/tfs/201707/t20170718_2652766.htm)：评审因素应与货物服务质量相关，包括投标报价、技术或服务水平、履约能力、售后服务等，并应细化量化、对应采购需求和商务条件。
- [《中华人民共和国政府采购法实施条例》](https://www.mof.gov.cn/zhengwuxinxi/zhengcefabu/201502/t20150227_1195516.htm)：政府采购对象和工程相关货物、服务有不同适用边界，工程建设相关内容需要单独识别，避免把施工组织设计类项目混入本 skill 的软件/货物模式。

## 分阶段使用指南

不要一上来要求 agent 直接写完整标书。推荐按阶段推进，每个阶段都留下可追溯产物。

### 1. 资料接收、外包审标、模式判断与工作区整理

目标：确认招标文件、附件、图纸、澄清文件、响应格式、模板和证据材料是否齐全；如果是外包/代写项目，先输出给客户的审标反馈包；并先判定投标模式。

推荐提示词：

```text
使用 $tender-bid-writer 整理当前工作区的招标资料。如果这是外包/代写项目，请先按前置审标流程输出招标文件审查报告、标书整体框架、评分点响应映射表、资料清单和对客户反馈话术。请识别招标文件、附件、澄清文件、格式模板和证据材料，判断本项目属于 goods-mode、software-platform-mode、hybrid-goods-software-mode 还是 service-mode，说明依据，建立 00_source 到 07_client_feedback 的工作目录，并列出缺失或无法读取的文件。
```

阶段产物：资料清单、投标模式判断表、招标文件审查报告、评分点响应映射表、客户材料清单、问题澄清清单、对外反馈话术、工作目录。

### 2. 需求抽取与三级细化

目标：先抽取评分标准、资格要求、技术参数、采购需求、商务条款和格式要求，再把采购需求细化到三级。

三级拆解建议：

| 层级 | 含义 | 示例 |
| --- | --- | --- |
| 一级 | 需求域、系统边界、平台或服务大类 | 数据中台、交易服务平台、运维服务 |
| 二级 | 功能、服务事项、控制对象或交付物组 | 数据治理、接口联调、故障响应 |
| 三级 | 最小响应单元，可写正文、可检查、可验收 | 主数据编码规则、接口异常重试机制、P1 故障处置记录 |

通用推荐提示词：

```text
使用 $tender-bid-writer 按已确认的投标模式抽取招标文件中的评分标准、资格要求、技术参数、采购需求和商务条款。采购需求必须细化到三级，并为每个三级需求标注来源页码/条款、响应章节、证据材料和验收关联。
```

阶段产物：评分台账、资格台账、技术参数台账、商务条款台账、采购需求三级分解表、证据矩阵。

### 3. 整体篇幅规划与章节 brief

目标：在写正文前先确定整标厚度、章节结构、每章目标、证据边界和验收输出。

规则：

- 若招标文件有页数上限、格式模板或固定响应表，优先服从招标文件。
- 若无硬限制，按投标模式规划整体篇幅。软件平台标和复杂混合标可按 `1 万元 ≈ 1 页` 并结合复杂度向上调整。
- 重大软件平台/复杂混合项目整套技术/商务响应原则上不低于约 `300-500 页`。
- 货物标不追求虚胖正文，重点保证参数响应、证据矩阵、偏离表和附件材料完整。
- 服务标按服务范围、人员投入、SLA、考核和记录要求确定厚度。
- 每个三级采购需求应有一个主响应位置，不能散落在多个章节无人负责。
- 结构先重平衡：普通章节轻展开，重点章节深展开；同级标题数量自然控制在 `2-6` 个之间，避免每组都 3 个或 4 个。
- 厚章节允许叶子标题落在不同层级，重点章节应同时存在 4 级、5 级、6 级叶子标题。
- 软件平台、数据平台、系统集成或复杂混合标中，六个优于招标专题要明显加厚：数据一致性校验、接口联调、新旧系统并行运行、切换演练、业务回退、过渡期运维。

推荐提示词：

```text
使用 $tender-bid-writer 基于需求台账生成投标文件整体框架和章节 brief。请先做结构重平衡：普通章节轻展开，重点章节深展开，同级标题数量在 2-6 个之间自然变化，不要平均铺开。对数据一致性校验、接口联调、新旧系统并行运行、切换演练、业务回退、过渡期运维六个优于招标专题加厚到 5-6 级结构。请给出整标页数预算、每章目标页数、三级采购需求映射、拟使用表格/流程图、证据需求和验收支撑材料。先不要写正文，等我确认框架。
```

阶段产物：目录框架、页数预算表、章节 brief、需求-章节映射表、证据需求清单。

### 4. 逐章厚标书正文编写

目标：按确认后的 brief 一章一章写，不写泛化模板。

正文要求：

- 正文主要写在最低层级的叶子标题下，不要每一级都平均铺正文。
- 最低层正文按重要性生成 `1-5 段`：普通范围类少写，数据、接口、回退、并行、过渡运维类多写；每段自然控制在约 `200-500` 字，不要固定字数。
- 优先使用 `机制 + 场景 + 表单 + 输出成果` 结构。
- 平台型软件项目要写到系统边界、数据链路、接口联调、数据迁移、主数据、质量追溯、业务连续性、演示功能等专项。
- 每个大章节至少配一个流程图和一个表格；表格用于职责矩阵、风险台账、验收映射、接口清单、数据校验、问题分级、交付材料等，不能只是装饰。
- 技术方案要像真人投标团队写出来的章节：少用“本项目属于……”“围绕……”“项目经理会……”“从以往经验看……”“控制要点1/细化核查1”等模板句，多写事项、机制、场景、记录和验收依据。
- 标题要场景化，不用“接口联调控制要点1”这类机械标题，优先使用“报文样例核对”“异常回执处理”“外部值守安排”“复测关闭口径”等可评审标题。

推荐提示词：

```text
使用 $tender-bid-writer 按已确认的章节 brief 编写《质量管理方案》正文。正文主要写在最低层叶子标题下，按重要性生成 1-5 段，每段约 200-500 字自然变化；普通范围类少写，数据、接口、回退、并行、过渡运维类多写。每个大章节至少配一个流程图和一个能支撑评分/验收的表格。写作时按真人投标方案口径处理：不要使用“本项目属于……”“围绕……”“项目经理会……”“从以往经验看……”“控制要点1/细化核查1”等模板句；标题要场景化，例如“报文样例核对”“异常回执处理”“复测关闭口径”。
```

阶段产物：单章正文、章节表格、过程记录模板、验收映射材料。

### 5. 章节自检与补强

目标：每章完成后先评审，不要直接合稿。

检查重点：

- 是否覆盖评分项、强制要求和三级采购需求。
- 投标模式是否正确，是否存在货物标被写成平台方案、平台标被写成参数表、混合标没有拆线、服务标硬套产品/软件模板等问题。
- 是否存在无证据承诺、草稿痕迹或虚构材料。
- 是否有足够项目场景，而不是通用软件工程模板。
- 章节结构是否重平衡，是否存在目录平均展开、同级标题都 3/4 个、叶子标题都落在同一级的问题。
- 六个优于招标专题是否明显加厚，是否达到 5-6 级且正文、表格、流程图、验收材料都比普通内容更充分。
- 最低层正文是否按重要性生成 `1-5 段`，而不是固定段数或每级都铺正文。
- 是否形成可验收、可追踪的输出物。
- 是否存在 AI 味句式：重复的章节导语、口号式闭环、抽象机制、机械标题、没有角色/阶段/记录/验收输出的空泛段落。
- 是否满足 Word 交付规则：使用 `投标文档格式.docx` 母版，Heading 1-9 承载 `TB_01`-`TB_09`，表格单元格用 `TB表格`，不手工写“第一章”“1.1”编号。

推荐提示词：

```text
使用 $tender-bid-writer 对刚完成的章节做章级评审和真人投标语感改写。请检查评分覆盖、三级采购需求覆盖、结构重平衡、六个优于招标专题厚度、叶子标题正文落点、1-5 段正文变化、表格/流程图支撑、证据缺口、草稿痕迹、跨章节冲突和验收追踪关系；同时标出“本项目属于”“围绕”“项目经理会”“从以往经验看”“控制要点1/细化核查1”等模板句，把它们改成采购人场景、执行阶段、责任角色、记录表单、问题处置和验收材料支撑的正式投标表达。
```

阶段产物：章级评审表、修订清单、证据缺口清单。

### 6. 合稿质检与专家评审

目标：合并章节后，从合规、技术、评分、交付、商务/法务角度模拟评审。

推荐提示词：

```text
使用 $tender-bid-writer 合并已确认章节并运行质检。请输出漏项、短章节、占位符、证据缺口、三级需求未响应项、页数不足项和跨章节冲突，再模拟五类专家评审并给出提分修订计划。
```

阶段产物：合稿文件、QC 报告、专家评审意见、提分修订计划。

### 7. 最终交付

目标：形成提交前清单，确认签章、附件、格式和未决事项。

Word 交付要求：

- 使用 `投标文档格式.docx` 作为母版；如果工作区没有该文件，先要求用户提供，不要假装已经套用母版。
- 标题使用 Word Heading 1-9 承载母版中的 `TB_01`-`TB_09` 样式关系；表格单元格文字使用 `TB表格`。
- 不要手工在标题里写“第一章”“1.1”“1.1.1”等编号，除非招标文件固定格式要求。
- 每个大章节单独输出一个 DOCX，并放入 `分章节定稿` 文件夹。
- 文件名使用两位前置序号，便于排序和合并，例如 `06-数据迁移与一致性校验-DG格式版.docx`。

推荐提示词：

```text
使用 $tender-bid-writer 准备最终交付清单。请核对最终文件、附件、响应表、证据材料、签章要求、格式要求、未决确认事项和提交风险。
```

阶段产物：最终交付清单、签章清单、附件清单、未决风险清单。

## 本地质检脚本

`scripts/bid_quality_check.py` 是一个无第三方依赖的辅助脚本，可以扫描草稿中的明显风险：

- `TODO`、`TBD`、`待补充`、`待确认` 等占位符。
- 过短章节。
- 需求文件和方案正文之间的覆盖缺口。
- 证书、资质、授权、案例、人员等证据引用不足。
- AI 味句式、机械标题、六个优于招标专题覆盖不足、长章节缺少流程图或评分/验收表格等问题。
- 章节结构、叶子标题正文、Word 母版样式和 `分章节定稿` 输出规则需要人工复核的事项。

示例：

```bash
python skills/tender-bid-writer/scripts/bid_quality_check.py \
  --workspace ./my-bid-workspace \
  --proposal ./my-bid-workspace/03_chapters \
  --requirements ./my-bid-workspace/01_requirements \
  --out ./my-bid-workspace/05_qc/qc_report.md
```

脚本只做机器粗筛，不能替代人工复核。正式投标前必须人工核对否决项、评分标准、格式要求、签章要求和所有证据材料。

## 安全边界

这个 skill 明确要求：

- 以招标文件为唯一事实源。
- 不编造资质、证书、案例、价格、工期、授权、签章状态或第三方承诺。
- 对缺失信息标记 `待确认`。
- 涉及否决项、资格风险、法律/商务承诺时先要求人工确认。
